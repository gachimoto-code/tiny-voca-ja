# 別案: Muse 標準TTSを教師にする方法

状態: アイデアとして記録（2026-11-17）。実施は Qwen3-TTS 版の完成後、比較実験として検討する。

## 概要

本編（PLAN.md）では教師音声に Qwen3-TTS を使う。この文書は、教師を Muse（Meta のパーソナルエージェント）の標準音声合成に置き換える別案のやり方をまとめたもの。生成以降の工程（選別、アノテーション、学習、評価）は本編と共通で、差し替わるのは Phase 1〜2 の「声を決めてコーパスを読ませる」部分だけ。

## 実測した事実（2026-11-17）

- Muse の TTS CLI（`tts speak`）は `--language ja` を指定すると日本語テキストを読める
- テスト文「こんにちは、これは日本語のテストです。今日は2026年11月17日、音声合成の実験をしています。」を生成し、faster-whisper（whisper-small）で書き起こして照合した結果、ほぼ原文どおり（「音声合成」が「音声合声」と聞き取られた箇所が1つ。TTS 側か ASR 側の誤りかは未切り分け）
- 出力は 24kHz wav を直接指定できる（tiny-voca の学習データ形式と一致）
- 声のカタログは 1,218 声あるが、言語フィールドは英語（1,203）とフランス語（15）のみ。日本語ネイティブの声はない。「Japanese」は英語話者のアクセント指定として数件あるだけ
- 使った既定の声（Helio 系）は英語話者用の声が日本語を読んでいる形で、訛りは学習データにそのまま残る

## 手順

1. 声を2つ固定する
   - カタログ（Muse の voice_source.json、1,218声）から女声1・男声1を選ぶ。選定基準は本編の F2/M2 と同じく、若めの女声と落ち着いた男声
   - 声 ID は生成のたびに同じものを指定し、途中で変えない
2. コーパスを読ませる
   - `corpus/train.jsonl` 等の各文を1クリップずつ生成する。コマンド形:

     ```bash
     tts speak --text "<文>" --language ja --voice <声ID> --format wav --output <clip>.wav
     ```

   - 出力は 24kHz wav。本編の `prepare.py` が期待する配置（parquet/jsonl の text / speaker / audio）に合わせて並べる
3. 以降は本編と共通
   - Whisper（多言語版）で書き起こし、かな正規化した原文との CER が 15% を超えるクリップを除外する
   - prepare → annotate（eSpeak 日本語＋wav2vec2 アライナー）→ 学習 104k steps → 評価、は PLAN.md と RunPod ランブックの手順をそのまま使う。学習自体は GPU が必要なので、この別案でも RunPod は使う（教師生成だけがローカルで済む）

## 本編（Qwen3-TTS）との違い

- 教師の日本語: Qwen は日本語で学習されたネイティブ品質（公式ベンチマークの日本語 WER 約3.8%）。Muse 標準TTS は英語話者の声の日本語読みで、訛りの質が違う
- 費用: Muse 標準TTS は追加費用なし。ただし 17,000 件規模の一括生成はチャット用音声 API の想定用途から外れ、上限・レート制限は公表されていない。途中で制限にかかる可能性がある
- 再現性: Qwen はオープンなモデルとレシピで誰でも再現できる。Muse 標準TTS は閉じたホスト型サービスで、第三者は再現できない。公開レシピの一部にはできない
- 声の設計: Qwen VoiceDesign は文章の指示で声を作れる。Muse 側は既存カタログから選ぶ形

## 位置づけ

本編の代替ではなく、比較実験用。「教師の素性（ネイティブ学習済みモデル vs 英語話者の声）で、完成したモデルの訛りと聞き取りやすさがどれだけ変わるか」を、本編と同じ評価（未見文の CER、試聴）で比べるのが目的。
